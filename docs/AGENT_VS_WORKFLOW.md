# Agent 与 Workflow 选择指南

## 1. 基本判断

Workflow 使用预定义控制流，适合步骤清晰、分支可枚举、结果可直接验证的任务。Agent 具有更高自主性，适合需要根据中间观察动态选择路径的开放任务，但会增加 token、延迟、调试难度和静默错误风险。

Shumo 的默认选择是 Workflow。

## 2. 快速决策表

| 判断问题 | 是 | 否 |
|---|---|---|
| 能否画出完整或近似完整决策树？ | Workflow | 继续评估 Agent |
| 任务是否影响核心模型、重大风险或创新价值？ | 继续评估 | Workflow |
| Agent 的关键能力是否经过测试？ | 继续评估 | 人工检查或 blocked |
| 重大错误是否可通过测试、残差、对照或回滚发现？ | Bounded Agent | Workflow 或人工检查 |

只有四项评估均支持 Agent 时，才启用 `bounded_agent`。

## 3. 数模任务分类

### Workflow 优先

- 题面解析和交付清单；
- 单位换算、参数表和文件 schema；
- 已选路线的模型规格化；
- 常规代码实现和批量运行；
- 结果残差、约束、边界和敏感性检查；
- 公式登记、编号和引用；
- 论文架构、写作和格式验收。

### Agent 候选

- 多条路线之间的开放探索；
- 从题目特有结构中寻找可验证改进；
- 未知原因的代码或数值异常诊断；
- 对关键方案构造反例和隐藏风险。

## 4. 常见误判

### “任务很长，所以需要 Agent”

错误。长流程只要步骤确定，就应拆成 Workflow。

### “使用 Agent 会自动更聪明”

错误。Agent 只是获得更多行动自由，并同时增加成本和错误路径。

### “最后有人看一遍，所以错误可控”

不充分。必须明确错误会通过什么测试或证据暴露，而不是依赖泛化人工复核。

### “为了创新，每题都运行探索 Agent”

错误。很多问题的成熟路线已经足够，强制探索只会制造复杂度和伪创新。

## 5. 推荐设计顺序

1. 先写清目标、输入、输出和成功标准；
2. 再设计环境和工具返回；
3. 建立确定性主流程和质量门槛；
4. 找出真正无法枚举的节点；
5. 只在这些节点放入受控 Agent；
6. 为每个 Agent 配置预算、停止条件、验证器和回滚点；
7. 从 Agent 的受限视角模拟完整任务，补齐认知缺口。

## 6. Shumo 推荐形态

```text
Workflow 骨架
├── 题目解析
├── 模型规格
├── 实现与求解
├── 验证
├── 登记与蓝图
└── 写作与交付

可选 Agent 插槽
├── 路线探索
├── 未知故障诊断
└── 方案压力测试
```

这使系统既保留开放问题处理能力，又能保持公式、结果和论文结构的可复现性。
