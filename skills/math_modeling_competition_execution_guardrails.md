# 数学建模竞赛 Skill 执行补充规则

本文件补充 `skills/math_modeling_competition_skill.md`。

## 1. 读取 skill 后必须按清单执行

当用户要求“严格按照数模 skill 进行”时，不能只读取 skill 后直接计算结果。必须把 skill 转化为执行清单，并按以下顺序组织任务：

```text
题目条件 → 问题分析 → 模型假设 → 符号定义 → 简图说明 → 公式推导 → 算法求解 → 数值结果 → 可靠性检验 → 模型评价
```

输出前必须检查每一项是否已经体现。若某项确实不适用，应说明原因；不能隐式跳过。

## 2. 禁止把完整数模任务简化为结果计算任务

若题目要求输出 Excel、代码、图像或数值结果，仍不能只完成计算和文件生成。正确顺序是：

```text
先建立论文结构 → 再建立模型 → 再配置示意图 → 再推导公式 → 再设计算法 → 再计算结果 → 再验证与评价
```

禁止顺序：

```text
先算结果 → 直接写结论 → 简略补文字
```

## 3. 简化示意图为几何与运动问题的强制项

凡涉及几何关系、空间位置、轨迹运动、路径规划、速度方向、碰撞检测、刚体连接、边界约束或坐标变换，必须先配置简化示意图，再写公式。

简图用于说明变量位置、方向、距离、边界和约束来源。图后必须回到数学公式，不能只靠图解释。

## 4. 示意图工具优先级与可编辑要求

数学建模论文中的简化示意图应优先使用真正便于人工拖动修改的图形工具，而不是把 HTML 作为默认主工具。

推荐优先级如下：

1. **draw.io / diagrams.net（首选）**：用于几何关系图、建模方法图、流程图、碰撞判定图、约束关系图。交付 `.drawio` 源文件，并导出 PNG 或 SVG 插入 Word。图中所有点、线、箭头、矩形、文字框、标注应为 draw.io 原生可编辑对象。
2. **PowerPoint 原生形状（次选）**：用于需要用户快速拖动修改的论文示意图。交付 `.pptx` 源文件，并导出 PNG 插入 Word。所有元素应为 PPT 原生形状，不能是整张图片。
3. **MATLAB 绘图代码（适合数据/几何计算图）**：用于需要按坐标或计算结果精确绘制的轨迹、几何图、碰撞结果图。必须保留完整可运行代码，参数集中定义。
4. **HTML/SVG（展示优先，不作为默认编辑工具）**：仅在用户明确要求浏览器前端编辑，或需要交互展示时使用。若使用 HTML，必须提供前端可视化控制区、可编辑输入框或可拖拽对象；不能只让用户进入源码修改。

不得只提供不可编辑截图、位图或静态图片。若给出图片预览，也必须同时提供对应的可编辑源文件。

## 5. 正式论文表达约束

数模 skill 的作用是帮助生成标准数学建模论文，而不是把执行约束、写作规则或思考过程写进论文正文。正式文档中不得出现类似下列元说明：

- “按照数模求解流程，应先配置简化示意图，再进行公式推导。”
- “为保证示意图可人工修改，本文同时提供 HTML/SVG 源文件与 MATLAB 绘图代码。”
- “根据 skill 要求，本节进行结构完整性检查。”
- “下面按照问题分析、模型假设、符号说明的流程展开。”

正式论文正文只能呈现研究对象、模型假设、变量定义、公式推导、算法说明、结果分析和模型评价。内部执行规则只用于保证输出质量，不应显性出现在正文中。

## 6. Word 与正式文档字体规范

生成 Word、论文正文、建模报告等正式文档时，默认采用以下字体规范：

1. 中文统一使用宋体。
2. 英文和数字统一使用 Times New Roman。
3. 表格、图题、表题、公式编号、脚注和正文中的变量说明均遵循上述中英文字体区分。
4. 若用户另行指定学校、竞赛或模板格式，则以用户指定模板为准，但仍优先保持中文宋体、英文和数字 Times New Roman 的基本规范。

## 7. 交付边界划分

生成数学建模相关成果时，必须先区分三类内容，避免混写：

1. 正式论文正文：只呈现问题分析、模型假设、符号说明、图表、公式推导、算法过程、结果分析、可靠性检验和模型评价。
2. 支撑材料：代码、draw.io 源文件、PPT 可编辑源文件、HTML/SVG、MATLAB 绘图代码、Python 求解脚本、Excel 结果表、图片源文件等。
3. 聊天回复：只说明交付了哪些文件、核心结论和下载入口，不替代正式论文正文。

制作要求、skill 约束、文件可编辑性说明、生成流程说明只属于内部执行或支撑材料说明，不得进入正式论文正文。

## 8. 图件交付验收标准

涉及几何、运动、路径、碰撞、空间关系的问题，图件必须至少满足以下要求：

1. 至少包含一张“建模方法示意图”，用于解释变量、对象、递推关系、约束来源和建模流程。
2. 若涉及判别或优化，应包含一张“判断条件示意图”或在建模图中明确体现判据，例如投影区间、可行域、边界条件、目标函数方向、碰撞筛选条件等。
3. 若有最终结果，可另设“结果示意图”，但结果图不能替代建模方法图和判断条件图。
4. 图题和图后文字必须服务于公式推导，而不是描述制图工具或编辑方式。
5. 首选交付 `.drawio` 源文件与对应 PNG/SVG 预览；若用户主要在 Office 中修改，则交付 `.pptx` 原生形状源文件与对应 PNG。
6. HTML 图只有在用户明确要求浏览器交互编辑时才作为主交付物；此时必须能在前端直接编辑关键文字、点、线、箭头、颜色、宽度、坐标、矩形或区域参数。
7. 若提供 MATLAB 图，必须保留完整可运行代码，并保持参数集中定义、图形比例正确、变量标注清晰。

## 9. Word/论文交付验收标准

生成 Word、论文段落或正式建模报告前，必须按以下标准自检：

### 9.1 正文结构

1. 一级标题、二级标题、三级标题层级清楚。
2. 单个问题至少包含：问题分析、模型假设、符号说明、模型建立、算法求解、结果分析、可靠性检验、模型评价。
3. 各小节之间存在自然承接，不能像清单堆叠。
4. 不出现“按照 skill”“为满足用户要求”“可人工修改”“我生成”等元叙述。

### 9.2 公式与变量

1. 公式从基本关系逐步推导，不突然给出最终模型。
2. 每个核心变量首次出现时有定义，并能追溯到题目条件、假设或前置公式。
3. 数值解必须说明初值、搜索区间、约束范围、求解器、停止条件和可行解筛选方式。
4. 必须讨论解的存在性、可行性、唯一性或物理可行根选择。

### 9.3 图表与结果

1. 正文必须给出题目要求的关键结果，不能只写“见附件”。
2. 结果表与 Excel、CSV 或其他附件结果完全一致。
3. 图表必须有编号、题名和正文引用，图题置于图下，表题置于表上。
4. 表格不只贴原始数据，应服务于结论表达。
5. 图必须解释模型或结果，不得只作装饰。

### 9.4 正式语言

1. 语言采用数学建模论文口吻，避免口语化、工具说明化和自我解释。
2. 不写“建议、参考、可以这样写”等非正式提示语，除非用户明确要求方案建议。
3. 不把内部检查清单、生成流程、代码文件说明写进正文。
4. 模型不足应真实但不否定核心结论。

### 9.5 格式

1. 中文使用宋体，英文和数字使用 Times New Roman。
2. 公式、表格、图题、表题、脚注和变量说明字体规范一致。
3. Word 文档应可直接打开，标题层级、段落间距、表格边框、图片比例正常。
4. 若用户指定模板、标题或格式，以用户指定要求为优先。

## 10. 支撑材料交付验收标准

若同时交付 Excel、draw.io、PPT、HTML、MATLAB、Python、图片等支撑文件，应满足：

1. Excel 文件保持题目模板的表名、表头、字段名、单位和顺序；数值精度与题目要求一致。
2. draw.io 文件可在 diagrams.net 中直接打开，图中对象应为可拖动、可改文字、可改样式的原生图元，不应嵌入整张不可编辑图片。
3. PPT 文件应使用原生形状、文本框、连接线和箭头；不得把整张示意图作为单一图片糊在页面上充当可编辑源文件。
4. HTML 文件可直接在浏览器打开；若用户要求前端修改，应提供可视化控制面板、可编辑输入框或可拖拽对象，而不是只给源码。
5. MATLAB 与 Python 代码应可复现正文核心结果；代码中的参数、文件名和输出结果应与正文一致。
6. 图片文件应与 Word 中插图一致；若图片来自 draw.io、PPT、HTML 或 MATLAB，应保留对应源文件。
7. 支撑文件的说明应放在聊天回复或附件说明中，不写入正式论文正文。

## 11. 最终回复验收标准

向用户交付最终文件时，回复应简洁，只列出必要下载链接和极简说明。若用户明确要求“只发 Word”，则只给 Word 下载链接，不附加额外解释。

若交付物存在不确定性、未完成项或工具限制，必须明确说明；不能假装已经完成。

## 12. 输出前结构检查

最终输出前必须检查：问题分析、模型假设、符号说明、建模方法图、判断条件图、公式推导、求解算法、初值与搜索区间、约束与停止条件、结果表、残差或合理性检验、模型评价是否完整。

该检查属于内部质量控制，不应以“检查清单”或“按照 skill”之类表述写入正式论文正文，除非用户明确要求展示检查过程。
