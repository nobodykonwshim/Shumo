# 数学建模写作与求解 Skill

## 适用范围

本 Skill 用于数学建模竞赛、数模论文撰写、模型审核、模型重写、结果解释、结果表格整理和答辩材料整理等任务。凡用户要求“使用数模 skill”“建模与求解”“论文版”“审核模型”“整理完整模型”时，均优先按本规范组织输出。

## 总体写作结构：总—分—总

每一个问题的解决必须采用“总—分—总”的结构，而不是直接堆公式或直接给结果。

### 1. 开头之“总”：问题解决思路总述

每一问开头先用一段完整文字说明：

- 本问要解决的核心目标是什么；
- 已知条件、约束条件和需要输出的结果是什么；
- 采用什么总体建模思路；
- 求解流程分为哪几步；
- 每一步之间的逻辑关系是什么。

开头总述应让读者在进入公式前已经知道“为什么这样建模、接下来要推导什么、最终如何得到结果”。

推荐句式：

> 本问的核心目标是……。为此，本文首先……，然后……，接着……，最后……。通过上述流程，可以将题目要求转化为……，并进一步得到……。

### 2. 中间之“分”：逐步模型推导

中间部分必须按步骤展开数学模型，不得遗漏关键推导，不得从结论跳到结果。

每一步至少包括：

1. 该步骤的建模目的；
2. 变量和参数定义；
3. 数学公式或约束关系；
4. 公式来源或推导过程；
5. 求解方法或数值实现方式；
6. 与下一步之间的衔接说明。

公式推导要求：

- 公式中出现的新变量必须及时解释；
- 单位必须统一，题目中 cm 应转为 m 后再参与计算；
- 关键约束不得只用文字描述，必须写成数学表达式；
- 涉及递推、优化、碰撞检测、速度约束、边界条件时，应明确索引范围；
- 涉及数值求解时，应说明搜索区间、精度、停止准则和误差检验方式；
- 不使用“显然可得”“容易得到”替代关键推导，除非该步确实非常基础。

推荐层级：

```text
X.1 本问求解思路
X.2 模型建立
    X.2.1 ……模型
    X.2.2 ……约束
    X.2.3 ……递推/优化/判定方法
X.3 模型求解
X.4 结果展示
```

### 3. 结尾之“总”：结果表格与结果示意图

每一问结尾之“总”应以结果呈现为主，直接列出本问的计算结果表格和结果示意图，不做过多文字解读。

结尾部分应包括：

- 题目要求的关键计算结果；
- 结果表格，例如位置表、速度表、参数表、误差表、最优解表等；
- 结果示意图，例如轨迹图、路径图、碰撞状态图、调头路径图、速度分布图等；
- 必要的简短说明，说明表格或图对应什么结果；
- 必要的误差检验或约束满足情况，可用表格列出。

结尾文字应简洁，不展开长篇机理分析，不重复模型推导，不写过多评价性语言。原则上采用“表格 + 图 + 1~2 句必要说明”的形式。

推荐句式：

> 按照上述模型求解，得到本问计算结果如表 X 所示，对应结果示意图如图 X 所示。由误差检验可知，结果满足题目约束和输出精度要求。

## 建模推导原则：按模型自然生成顺序书写

当前 Skill 对建模过程有强约束：数学模型必须按照“模型自然生成顺序”一步步推导出来，不能为了尽快解决问题而把后面才需要的判定条件、数值算法或结论提前放到模型建立的前面。

### 1. 每个小节先明确“要建立什么模型”

每个模型小节开头必须先说明本小节的目标，例如：

- 本小节建立龙头运动模型；
- 本小节建立相邻把手位置递推模型；
- 本小节建立板凳矩形表示模型；
- 本小节建立碰撞判定模型；
- 本小节建立终止时刻搜索模型。

说明目标后，再从题目条件、几何关系、物理约束或优化目标出发推导，不能一开始就直接给最终判别函数或最终算法。

### 2. 严禁“后置条件前置”

写作时不得把后面阶段的条件提前塞进前面模型。例如：

- 还没有建立板凳几何区域时，不应直接写碰撞判定函数；
- 还没有得到单对板凳碰撞判据时，不应直接定义全局终止时刻；
- 还没有明确速度递推关系时，不应直接讨论最大速度约束；
- 还没有建立路径几何约束时，不应直接给出最短路径结论。

正确顺序应是：先定义对象，再建立几何或物理关系，再得到局部判据，再组合成全局判据，最后给出数值求解方法与结果。

### 3. 以最少公式解决问题

建模的核心目标是用尽量少但必要的公式解决问题，而不是堆砌大量繁杂公式。公式使用遵循以下原则：

- 能用一个核心公式表达的，不拆成多个重复公式；
- 能用文字说明的普通代数步骤，不强行写成公式；
- 只保留支撑模型成立和结果可复现的关键公式；
- 复杂展开式若不直接用于计算或论文表达，可放入算法描述或附录，不放在正文主体；
- 每个小节一般围绕 1--3 个核心公式展开，除非题目本身必须进行完整推导。

公式不是越多越好。好的建模应当是逻辑清楚、公式精炼、推导连续、结果可复现。

### 4. 正确推导顺序模板

每个模型小节建议按以下顺序写：

```text
（1）说明本小节要建立的模型；
（2）定义该模型需要的对象、变量和参数；
（3）从题目条件或几何/物理关系推出第一个核心关系；
（4）在该关系基础上继续推出本小节最终模型；
（5）说明该模型如何被下一小节使用。
```

例如，碰撞检测模型不能直接从“全局碰撞函数”开始，而应按：

```text
板凳几何区域表示 → 候选板凳对筛选 → 单对板凳精确判定 → 全局碰撞判据 → 终止时刻搜索
```

例如，运动递推模型不能直接从“所有把手递推公式”开始，而应按：

```text
龙头位置 → 单节板凳刚性约束 → 相邻把手位置关系 → 逐节递推 → 速度约束求导 → 速度递推
```

### 5. 模型与算法分开写

正文中应区分“模型建立”和“算法求解”。模型建立部分回答“为什么是这个数学关系”，算法求解部分回答“怎样把这个关系算出来”。不要把搜索精度、扫描步长、二分法、程序实现细节提前混入模型定义。

推荐写法：

- 模型建立：写变量、几何关系、约束、目标函数或判定函数；
- 模型求解：写扫描、二分、优化、迭代、误差检验和文件输出。

### 6. 公式出现时机：按使用时点推导

公式不仅要按逻辑顺序推导，还必须在真正需要使用它的位置再出现。不得因为后文会用到某个公式，就在前文提前推导。公式放置原则为：当前小节需要什么，就推导什么；后面小节才需要的公式，后面再推导。

具体要求：

- 位置模型只推导位置、几何、弧长、距离约束等当前用于确定位置的公式；
- 速度模型应在已经得到位置关系之后，再推导速度向量、角速度、速度约束和速度递推；
- 碰撞模型应先建立板凳几何区域，再推导碰撞判定，不得提前定义全局终止时刻；
- 优化模型应先定义决策变量和可行域，再写目标函数、约束和算法；
- 暂时不用的公式不提前写，除非其本身是当前模型成立所必需的中间关系。

以板凳龙问题一为例，正确顺序应为：

```text
龙头位置模型：螺线方程 → 弧长微元 → 积分得到弧长函数 → 龙头角参数 → 龙头位置
相邻把手位置递推模型：把手编号 → 孔距 → 刚性距离约束 → 角参数增量 → 位置递推
把手速度递推模型：已知位置后再求速度 → 龙头速度约束 → 一般速度表达式 → 刚性方向速度差为零 → 速度递推
```

该原则优先级高于“集中推导公式”。写作时应避免在一个小节开头一次性给出大量后续才会使用的公式。

## 求解思路流程图要求：Draw.io

每一个数学建模问题都必须绘制“求解思路流程图”，并将流程图插入该问正文中。流程图作为“总—分—总”结构中开头总述与中间模型推导之间的桥梁，用于直观展示本问从已知条件到模型建立、数值求解、结果输出的逻辑链条。

### 1. 插入位置

流程图应放置在每一问的“本问求解思路”之后、“模型建立”之前。推荐正文结构为：

```text
X.1 本问求解思路
    用一段话总述目标、思路和流程。
    插入：图 X 问题X求解流程图
X.2 模型建立与推导
X.3 模型求解
X.4 结果展示
```

图前应简短说明绘图目的，例如：

> 为展示本问建模与求解流程，绘制问题 X 的求解流程图，如图 X 所示。

图后只需简短承接，例如：

> 图 X 给出了本问从输入条件到结果输出的主要计算流程。

### 2. 绘制工具与文件要求

流程图应使用 draw.io（diagrams.net）绘制，并至少保留两类文件：

- `*.drawio`：源文件，便于后续修改；
- `*.png` 或 `*.svg`：导出文件，用于插入 Word、PDF 或 LaTeX 论文。

推荐命名方式：

```text
p1_flow.drawio
p1_flow.png
p2_flow.drawio
p2_flow.png
p3_flow.drawio
p3_flow.png
```

当用户要求“Word版”“论文版”“完整建模与求解”时，应在最终文档中插入对应流程图；若当前环境无法直接生成 draw.io 源文件，应至少给出可直接转换为 draw.io 的流程图结构，并在可生成图片时同步插入图片。

### 3. 流程图内容要求

流程图必须与正文建模步骤一一对应，不能只画空泛流程。流程图节点应尽量简洁，通常只保留标题级节点，不在节点内堆砌公式或长句。

通常可包含以下节点：

1. 题目输入与已知条件；
2. 参数换算与符号定义；
3. 核心模型建立；
4. 约束条件构建；
5. 递推、优化、搜索或判定算法；
6. 数值求解与结果输出；
7. 误差检验；
8. 结果展示。

不同问题应突出不同重点：

- 轨迹或运动问题：突出“轨迹方程 → 位置递推 → 速度递推 → 结果输出”；
- 碰撞或终止问题：突出“几何表示 → 候选筛选 → 精确判定 → 终止时刻搜索 → 结果输出”；
- 优化问题：突出“决策变量 → 目标函数 → 约束条件 → 搜索/优化 → 最优性验证”；
- 路径设计问题：突出“几何约束 → 相切条件 → 曲线参数求解 → 路径长度/可行性分析”；
- 最大速度问题：突出“单位速度场 → 速度比例系数 → 最坏把手识别 → 最大龙头速度”。

### 4. 图题与图文规范

流程图图题统一写为：

```text
图 X  问题X求解流程图
```

其中 X 与论文中的问题编号一致。

流程图应保持清晰、简洁、黑白打印友好。节点文字应使用论文中的关键词，不使用过长句子；流程方向应从上到下或从左到右，避免交叉线过多。颜色可使用蓝色系作为主色，红色用于关键判定或终止条件，但不能依赖颜色表达唯一含义。

## 数模论文表达规范

1. 先建模，后求解，再展示结果。
2. 建模过程必须按模型自然生成顺序书写，不能把后面条件提前放到前面。
3. 公式应少而精，只保留解决问题所必需的核心公式。
4. 公式必须按使用时点出现，后面才需要的公式不得提前推导。
5. 关键数学步骤不能省略，例如积分、求导、投影、取模、代入、递推等应在文字或公式中交代清楚。
6. 结果不能孤立出现，但解释应简洁，避免在结果部分写过长分析。
7. 表格前要说明表格展示什么，表格后只需给必要说明。
8. 图前要说明为什么画图，图后只需给必要说明。
9. 不写口语化表达，例如“我们发现”“可以看到一点点”等，应使用“结果见表”“示意图如图所示”“误差检验见表”等。
10. 不夸大模型效果，不声称没有验证过的结论。
11. 若结果来自程序，应补充数值误差、约束满足情况或稳定性说明，优先用表格呈现。

## 数值求解与结果校验要求

只要涉及数值计算，就应尽量给出校验指标。例如：

- 约束误差：检验几何约束、距离约束、边界约束是否满足；
- 速度误差：检验速度大小、速度上限或速度递推是否满足；
- 目标函数值：检验优化问题求得的解是否合理；
- 稳定性检验：检验步长、精度、初值变化对结果的影响；
- 文件完整性：检验结果文件是否覆盖题目要求的全部时刻、全部对象和指定精度。

误差检验应优先以小表格形式给出，并放在每一问结尾结果展示部分。

## 板凳龙类问题专用要求

处理“板凳龙”问题时，应特别注意：

1. 所有长度统一使用 m；
2. 龙头板长、龙身板长、孔中心距必须正确换算；
3. 把手编号必须与题目一致；
4. 位置结果与速度结果应严格对应题目指定时刻；
5. 若使用递推模型，应说明唯一解选取原则；
6. 若涉及碰撞，应按照“板凳几何表示 → 候选碰撞筛选 → 单对板凳精确判定 → 全局碰撞判据 → 终止时刻搜索”的顺序建模；
7. 若涉及调头路径，应说明切点、相切条件、半径约束和路径唯一性；
8. 若涉及最大速度，应说明速度比例关系或最坏时刻、最坏把手的判定方式；
9. 每一问结尾优先给出题目要求的结果表格和运动/路径/速度示意图，解读控制在少量必要文字内；
10. 问题一类运动递推写作中，龙头位置模型只推导位置所需公式，速度公式应放在速度递推模型中再推导。

## 输出风格

当用户要求“论文版”“完整建模与求解”“可以写入论文”时，输出应直接采用论文正文风格，不写操作建议式语言。

当用户要求“审核”时，输出应先给核心问题，再按模型完整性、推导严密性、求解可复现性、结果可信度、论文表达规范进行评价。

当用户要求“Word版”或“文档版”时，应生成可下载文档，并尽量保持公式可编辑、表格规范、图表标题完整；每一问均应插入对应 draw.io 求解流程图或其导出图片；每一问结尾应以结果表格和结果示意图为主，不做过多文字解读。
